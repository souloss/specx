# Frontend Internationalization Conventions

The shared frontend supports Simplified Chinese (`zh-CN`) and English (`en`). These rules keep language resources complete and ensure user-facing strings remain independent from domain data and API control flow.

## Runtime and Resource Ownership

- Locale resources live in `apps/desktop/src/i18n/locales/zh-CN.ts` and `en.ts`; runtime setup and locale persistence live in `apps/desktop/src/i18n/index.ts`.
- The default and fallback locale is `zh-CN`. The selected locale is persisted as the device preference `specx-locale`; never store the active locale as workspace data.
- The Chinese resource defines `MessageSchema`; the English resource must match its key structure. `MessageKey` gives typed paths to `translate()`.
- Keep keys grouped by feature or shared context, use stable camelCase names, and prefer an existing semantically correct key over a duplicate. Avoid ambiguous catch-all keys for unrelated screens.

## Adding or Changing Text

1. Add the same key to both locale files in the same change. Chinese is the default resource and the source of the structural TypeScript schema.
2. Render strings through `translate("namespace.key")` or the existing Vue i18n integration. Do not hardcode user-visible strings in templates, dialogs, tooltips, notifications, or accessibility labels.
3. Use named interpolation such as `translate("sidebar.tag", { name })`; do not concatenate translated fragments. Keep placeholder names identical across locales. For counts, use the existing Vue I18n plural form conventions.
4. Pass the active locale to date/number formatting helpers where available. Use `formatDate` from `apps/desktop/src/lib/core.ts` for dates displayed by the application.
5. Keep workspace data such as service, group, tag, and specification names/content as user data. Do not add user-provided content to locale resources or translate it automatically.
6. API error handling uses stable error codes and locale keys, not message text. See [the API contract](api-contract.md) for the current v1 envelope and [the error contract](api-error-contract.md) for validation and code rules.

## Verification

`apps/desktop/src/i18n/index.spec.ts` checks runtime locale switching, persistence, error localization, plural behavior, and parity between locale key paths and named interpolation placeholders. Run `pnpm --dir apps/desktop test` and `pnpm --dir apps/desktop build` after locale changes.

When adding another locale, update `AppLocale`, the supported locale list, fallback policy, resources, locale selection UI as applicable, and the parity tests in one change. Do not claim support until all visible keys and placeholders are covered.
