# 规范与面板扩展模型

## 目标

扩展模型服务于“服务 → 规范/面板”的主路径。扩展可以贡献一种规范类型、一个渲染器或一个服务面板，但不能复制租户、工作区、服务和权限事实。

| 概念 | 责任 |
|---|---|
| Specification kind | 规范类型的稳定标识和元数据 Schema，如 `markdown` |
| Contribution | 可发现的能力，如 `spec.preview` 或 `service.panel` |
| Provider | 实现一个或多个贡献或外部能力的可替换实现；不等于服务本身 |
| Installation | 管理员批准的包和版本；一期不提供任意安装市场 |
| Workspace binding | 某工作区启用某贡献的授权选择 |
| Controller | 观察资源并协调 Provider，写回状态和快照；不直接拥有资源事实 |

## 一期贡献

Markdown 作为内置贡献实现预览。它接收已授权的规范内容和有限的服务上下文，返回安全的渲染结果或诊断。渲染器不能直接访问数据库、租户令牌或任意文件系统；Core 负责保存内容和授权，Host 负责挂载面板。

贡献与控制器是两种不同的扩展：贡献通常是同步的展示或纯内容处理；控制器负责异步观察、重试和状态写回。仓库同步控制器可以调用 Git Provider 生成 `RepositorySnapshot`，Markdown 文档同步控制器再消费快照并追加规范修订。控制器之间通过资源和持久事件协作，不在贡献或 Provider 中硬编码下游领域。

## 发现与故障

贡献按 `contribution_id`、规范类型、协议版本和授权状态发现。没有匹配实现时返回明确的 `capability_unavailable`，不伪造空结果。Provider 停用或失败不应删除服务、规范和已有内容；面板显示错误并保留回退阅读路径。

## 后续扩展

未来可以增加 OpenAPI、AsyncAPI 或服务专属面板，也可以接入代码仓库采集、搜索和分析控制器。但每种扩展都要独立声明数据所有者、权限、支持范围、故障边界、幂等语义和迁移方式。扩展名称不能成为主导航条件，Core 不能为某个 Provider 写专属分支。
