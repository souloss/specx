# OpenAPI 规范管理技术方案

状态：实施中。OpenAPI 类型、创建/更新 API、仓库文件发现、可展开的服务规范树、JSON/YAML Tag 导航、服务级环境和支持 JSON/YAML 高亮与格式化的原文编辑器已接入。Operation 叶子提供独立的调试、设计和文档 Tab；接口设计修改限定在当前 Operation 内；数据模型目录另行维护公共 Schema、引用导航及模型生命周期。持续演进的能力与缺口以[产品验收矩阵](openapi-product-gap-analysis.md)为准。

## 目标

在现有服务、Markdown 规范、仓库快照和修订能力上，增加 OpenAPI 规范的完整生命周期：创建或导入、解析校验、查看、编辑、仓库同步、历史恢复、按 Tag 浏览 API 定义，以及基于服务环境发送请求。

创建流程默认从本地文件导入，并复制为由 SpecX 管理的规范内容；用户可自定义导入后的规范标题。也可以选择服务仓库中的 branch/tag 和文件路径作为持续同步来源，或切换为直接在 SpecX 中录入。各来源按规范类型校验文件扩展名与内容，仓库路径和版本在保存前校验。

开始 OpenAPI 纵向开发前，先完成资源导航与内容加载的基础调整。OpenAPI 不能被当作另一种 Markdown 预览：它需要按规范结构生成目录和操作视图，同时保留原始定义作为可编辑、可同步、可恢复的权威内容。

## 平台能力提炼

参考 Apicurio Registry、APIlayer、Hoppscotch、YApi、Postcat、Grapity 等 API 管理平台后，当前 OpenAPI provider 只吸收跨产品稳定且能服务于资源管理的公共概念：规范目录、Tag/操作投影、服务器地址、环境变量、认证方案、请求执行和响应检查。provider directory 是服务目录的只读投影；它由规范内容派生，不把每个 Tag、operation 或 schema 变成 Core 资源。

环境是服务级的请求上下文，由名称、Base URL、启用变量和平台 Secret 引用组成。它用于 Try it 和后续请求工具，不是 StorageClass，也不要求用户选择底层存储。ContentStore、快照、Secret 加密和生命周期继续由平台统一管理，provider 只声明所需能力并通过受控接口使用它们。这样既保留统一资源治理、审计和权限边界，也允许未来为 GraphQL、AsyncAPI 或分析产物增加同样的 provider 投影。

Try it 只在用户明确发送时解析环境并执行一次浏览器/Host 请求。服务器地址在 API 写入边界和前端发送边界都限制为 HTTP(S) 或相对路径；平台不提供任意目标 URL 的服务端代理，避免把环境配置变成 SSRF 入口。

## 当前实现检查

| 边界 | 当前事实 | 对 OpenAPI 的影响 |
| --- | --- | --- |
| 服务目录 | `ServiceGroup` 支持无限层级；服务可展开，规范实现将分类、规范、Tag 和操作节点投影到侧栏。 | Core 继续只保存真实服务和规范；虚拟节点由规范实现生成并通过稳定身份打开对应视图。 |
| 规范模型 | Core 的 `SpecificationKind` 支持 Markdown 与 OpenAPI；正文和修订作为文本保存。导航标签可指向服务、规范、分类/Tag 目录或具体操作。 | 按规范类型解析和呈现；OpenAPI 操作视图仅展示选中操作，不重复展示整个文档。 |
| 规范 API | 规范创建/更新、ETag、修订、恢复、仓库来源及 OpenAPI 语义校验已接入。 | 复用生命周期和并发语义；Markdown 保持原行为，OpenAPI JSON/YAML 在写入边界校验。 |
| 仓库同步 | Repository Controller 提供通用文件快照；文件发现接口列出 Markdown、JSON 和 YAML 文件，来源路径与正文按规范类型校验。 | 文档同步按规范类型消费通用快照；不让 Repository Controller 理解 OpenAPI 语义。 |
| 目录载荷 | `/catalog` 中每个 `SpecificationResponse` 都带完整 `content`。 | 文档数量和体积上升后，启动和切换工作区会下载并保留全部正文；需要摘要列表和按需读取。 |
| 环境与执行 | 已有工作区级 Secret/Integration，凭据加密保存且列表只返回元数据；没有服务环境资源或 API 请求执行能力。 | 环境配置、Secret 使用范围和请求执行位置需要单独定义，不能复用 Git 凭据语义。 |
| 内容布局 | `ServicePanel` 的概览和规范面板同时承担 `max-width: 1100px` 和滚动容器职责；外层 main pane 还有响应式 padding。 | 窄内容容器居中时滚动条随容器居中，视觉上离主窗格右边缘较远。 |

`/api/specx/openapi.json` 是 SpecX 自身 HTTP API 的契约，不是用户服务的 OpenAPI 规范。

## 推荐资源树

把持久化资源关系和导航视图节点分开：Core 继续保存 Service、Specification 等有独立生命周期的资源；每个规范实现根据自己的内容返回服务下的导航投影，侧栏只负责承载、排序、筛选和打开这些节点。第一版不建立万能目录表，也不把每个 API 操作拆成数据库资源。

```text
Workspace
└── ServiceGroup（现有，可无限嵌套）
    └── Service（服务概览视图，可包含子节点）
        ├── Markdown Provider（自动创建，带提供者图标）
        │   ├── README（规范叶子）
        │   └── Guide（规范叶子）
        └── OpenAPI Provider（自动创建，带提供者图标）
            ├── OpenAPI Specification（规范目录/概览）
            │   ├── Tag Directory（目录视图）
            │   │   ├── GET /users（API 定义视图，可执行）
            │   │   └── POST /users（API 定义视图，可执行）
            │   ├── 未分类 API（没有 Tag 时的保留目录）
            │   └── 数据模型（公共 Schema 目录）
            │       ├── User（字段预览/公共设计/使用位置）
            │       └── ErrorResponse
            └── Other OpenAPI Specification（同一提供者目录下的另一份规范）
```

### 节点与身份

- `ServiceGroup` 仍然表示工作区中的服务组织路径；`Service` 不增加 `parentServiceId`。服务变成树中的可展开父节点，是因为它拥有规范子资源，不表示服务可以嵌套创建另一个服务。
- `Specification` 是服务下的真实子资源，但它如何出现在服务下面由规范实现决定。实现可以返回一个叶子、一个目录，或带有任意深度受限的目录/叶子组合；通用导航层不判断 Markdown、OpenAPI 或其他格式的语义。
- 每个规范提供者都必须在服务下提供一个稳定的虚拟提供者目录；目录名称和图标来自注册元数据，目录只在该服务拥有对应规范时创建。它保证同一类型的多个规范不会与其他提供者混在一起，也不把提供者事实写入 `Service`。
- Markdown 提供者目录下放置规范标题叶子；OpenAPI 提供者目录下放置规范目录、Tag 目录和操作叶子。其他提供者沿用相同投影契约，可以返回自己的目录和叶子结构。
- Tag 目录与 API 操作是由特定规范版本派生的虚拟导航节点，不单独写入 Core。工作区服务标签与 OpenAPI 的 `tags` 是两个不同概念，界面应使用不同样式或分组避免混淆。
- API 操作的稳定键使用规范 ID 加 HTTP method 和规范化 path。`operationId` 可用于显示、搜索和代码生成，但它在 OAS 中可缺省且不保证唯一，不能作为唯一身份。
- 一个操作带多个 Tag 时，各 Tag 下可以出现指向同一操作身份的导航别名；操作标签页去重。没有 Tag 的操作放入默认目录。Tag 顺序优先使用文档声明顺序，未声明的 Tag 再按稳定规则排序。
- 所有目录节点都可以展开，也可以打开自己的目录/概览视图；叶子节点打开自己的详情视图。展开控件和选中行为必须分离，避免目录节点只能展开而无法查看。

规范实现应提供一个通用的导航贡献契约，概念上包含：`providerKind`、可选 `categoryKey`、节点类型（`directory`/`leaf`）、显示信息、稳定 `identityKey`、父节点、来源 `specificationId`、内容 hash 和节点能力（打开、编辑、同步、执行等）。`ResourceTreeNode` 和面板标签应消费这个判别联合，而不是写死 `openapi-tag`、`openapi-operation` 等业务类型。派生节点引用其来源规范 ID 和内容 hash，不依赖标题、分类名或当前数组位置作为身份。

工作区切换和内容更新时，旧派生节点需按 hash 失效；若同步删除了已打开节点，标签显示“定义已从当前版本移除”，不能静默切换到同名节点。目录节点的视图由规范实现提供，通用层只传递节点引用和能力声明。

此方案将“服务虚拟路径”解释为服务成为规范实现投影的承载父节点，并复用现有分组构成服务之前的目录路径。服务不承担规范语义，也不支持在服务下创建嵌套服务；不同规范类型、文件分类和内容结构由对应实现返回。

## OpenAPI 文档与生命周期

### 权威内容

`Specification` 继续作为规范身份、类型、服务归属、当前内容摘要、ETag 和修订历史的权威资源。增加 `OpenApi` 类型，正文保存用户原始 JSON/YAML；解析出的目录、Tag 和 operation index 是可重建投影，不替代原始正文。

写入和同步必须经过同一格式校验路径：

1. 校验大小、编码、JSON/YAML 语法和 OpenAPI 结构。
2. 生成可展示的规范摘要及操作索引；操作的 path、method、Tag 和 `operationId` 不满足基本约束时返回带字段路径的验证错误。
3. 只有验证成功才通过现有 ETag/CAS 事务更新规范与追加修订。
4. 对仓库托管内容，解析失败时保留当前有效版本和修订；将失败写入同步诊断，不把无效正文覆盖到当前资源。
5. 内容 hash 未变时更新同步证据但不追加重复修订。

首版建议支持 OpenAPI 3.0.x、3.1.x 的 JSON 和 YAML，拒绝或明确报告不支持的版本。`$ref` 首版只解析文档内引用，不从网络抓取外部引用；这样目录生成和验证不会触发隐式网络请求或 SSRF。解析需限制输入字节、引用深度和总操作数，并检测本地引用循环。

手动维护和仓库托管继续沿用现有来源模式。手动规范可编辑、查看修订并恢复；仓库托管规范只读、可同步和解除来源。更新型绑定使用 branch 或 tag；固定 commit 可作为历史/来源证据展示，不作为自动跟随配置。OpenAPI 文件候选扩展为 JSON/YAML 格式并通过解析确认，而不是仅凭扩展名判定有效。

### 视图

| 节点 | 主视图 |
| --- | --- |
| Service | 服务概览、仓库状态、规范入口、服务环境摘要 |
| Specification Provider | 提供者图标、名称、规范数量和状态摘要；由注册元数据稳定生成 |
| Markdown Specification | Markdown 阅读/编辑、修订历史和来源状态 |
| OpenAPI Specification | 基本信息、版本/服务器、Tag 与操作目录、来源/校验状态、原文查看/编辑 |
| Tag Directory | 该 Tag 下操作清单、method/path/summary 搜索和数量 |
| Model Directory | 搜索模型名称、说明和字段；新建公共模型；由 `components.schemas`（兼容发现 `definitions`）派生 |
| Schema Model | 完整字段预览、源码查看、引用模型和使用位置跳转；公共模型设计、改名与删除保护 |
| API Operation | 三个独立 Tab：调试工作台选择环境、填写请求并检查响应；设计维护当前操作的元信息、参数、请求体和响应 Schema；文档预览展示 method/path、描述、参数、请求体、认证要求、响应和 Schema 字段 |

三个页面共用顶部的接口标识和位置固定的 Tab 栏；接口的完整描述、版本和标签位于文档页面内。桌面工作台将请求与响应并列，窄窗口顺序堆叠。

API 操作文档应包含 path/query/header/cookie 参数、请求体 media type/schema/example、响应 status/media type/schema/example、安全要求和服务端定义。引用 Schema 至少展示名称、类型、字段名、字段类型和必填标记；完整模式再递归展开嵌套字段。调试工作台与文档预览使用同一操作身份，但以独立 Tab 页面承载请求状态，避免请求响应、Secret 和编辑输入污染只读文档。首版不执行 OpenAPI `links`、回调、webhook，也不抓取远程示例或外部 `$ref`。

设计 Tab 的写入范围限定为选中的 Operation：只修改元信息时保留原始 `$ref`；修改共享 Schema 时将其拷贝到此 Operation 的请求体或响应中，再应用变更，公共模型、其它响应和相邻 Operation 保持不变。来自共享 Request Body/Response 的 Schema 使用相同规则。路径级继承参数保持只读；`oneOf`/`anyOf`/`allOf` 可维护分支，嵌套本地引用在本 Operation 内展开。循环、外部、无法解析的引用和条件/动态 Schema 仍只读。OpenAPI 3.0 忽略引用旁的 sibling 关键字；3.1 将其保留为交集约束，避免局部编辑放宽原模型要求。Operation 页仅显示接口级操作；整份规范的原文编辑、删除、历史和绑定入口位于规范根节点。

可编辑的规范根节点提供“新增接口”：录入 method、path、摘要与 Tag，校验重复路由及等价路径模板，为未被继承参数覆盖的路径占位符生成必填 string 参数。创建只新增一个 Operation；成功后打开该叶子，失败保留输入供重试。保存与原文更新共用规范 ETag、服务端校验和修订，不新增独立 Operation 数据表。

设计页允许修改当前 Operation 的 method/path。移动路径时将原路径继承的参数和服务器定义保留在当前操作内，操作级参数优先；保留不变的占位符名称后再匹配重命名参数，保留类型和约束，删除失效的路径参数并补充新增参数。相邻操作、公共模型和原路径元信息保持不变；本地 `$ref`/`operationRef` 地址跟随移动，被其它定义引用的已移除参数转存到 `components.parameters` 后更新引用，示例与默认值中的字面数据不改写。目标冲突、等价模板或引用型 Path Item 会阻止保存；带共享元信息的同形路径重命名仍需原文编辑。成功后更新现有标签页身份与目录，避免旧、新地址重复打开。

设计草稿按工作区、规范、Operation 隔离，在当前设备恢复，涵盖三个视图切换、切换接口和刷新；尚未填完或不合法的字段输入也保留。浏览器存储失败时只在当前页面内保留，界面不会声称已持久保存。其他 Operation 更新后，草稿应用在最新规范上；所选 Operation、路径级参数、OpenAPI 版本或公共模型变化时显示冲突并禁止直接覆盖，允许下载草稿或显式放弃草稿后加载最新定义。保存使用当前规范 ETag，不复用或覆盖独立的原文编辑草稿；412 后尝试刷新并保留接口草稿。草稿是当前设备偏好，不是服务器共享资源，跨设备恢复与自动冲突合并尚未接入。

字段编辑优先展示名称、必填、类型和说明；格式、标记、枚举、默认值、范围等收在原生可展开的“更多字段设置”中，摘要显示已配置数量。组合分支与子字段保留结构层级；页面保存工具栏随滚动保留。参数可维护 `style`、`explode`、`allowReserved`；响应状态码可修改，修改时保留完整响应内容，切换至 1xx/204/304 时移除正文。支持 nullable/readOnly/writeOnly/deprecated、独占数值边界及 additionalProperties，按 3.0/3.1 的 wire 语义保存。

修订恢复与仓库同步保持规范类型，不把 OpenAPI 改为 Markdown。恢复操作在同一历史弹窗内进入确认步骤，取消时返回所选修订并恢复按钮焦点，避免叠加弹窗互相隐藏无障碍节点。

### 公共数据模型

数据模型是 OpenAPI provider 从 `components.schemas` 生成的目录和叶子投影；同时发现旧文档的 `definitions`。目录和模型面板分别使用 `modelsDirectory` 与 `modelRef` 标识，模型引用采用规范内的 JSON Pointer；它们不复用 `operationKey`，也不新增模型数据库表。目录搜索覆盖名称、说明和字段，侧栏按接口摘要/Operation ID/模型字段搜索时保留祖先，并可叠加服务标签筛选。

模型文档显示完整属性、必填、约束、描述、解析后的 Schema 和原始定义。引用按钮跳转所属模型（含指向模型子字段的引用），使用位置区分直接引用和通过公共模型的间接引用；关联 API 打开对应 Operation 叶子。`allOf` 合并字段仍保留显式的引用模型入口。递归模型保留字段及跳转，在已访问模型处停止重复展开；OpenAPI 3.1 的布尔模型分别标为允许任意值与不允许任何值。

公共模型设计与 Operation 局部设计有不同的影响范围：模型页修改共享 Schema，会影响所有引用它的接口；界面明确显示影响数量。可视字段编辑复用现有 Schema 编辑器，完整定义可用 JSON/YAML 高亮、格式化和互转；保存前复用受限 Worker 校验。对引用字段的编辑只在当前模型内展开，不写入被引用模型。新建、更新、改名和删除均通过现有规范更新、ETag 和修订链路保存整份规范。

接口请求、响应、参数和递归字段的类型选择器可引用当前规范的公共模型。选择器按名称、说明和字段搜索，展示完整字段预览；确认才替换当前位置的结构，取消或再次选择原引用不产生修改。更换已有引用时保留 OpenAPI 3.1 Schema 的附加约束，OpenAPI 3.0 中没有 Schema 语义的引用兄弟字段不迁入新结构。原生单选控件支持键盘选择，预览与模型目录独立滚动；窄窗口上下排列并保留确认入口。公共模型设计使用同一编辑器，也可复用其他模型。

设计草稿保留原始 Schema 与 `$ref`，不把显示时展开的字段保存为引用状态。只改接口元信息时，引用及其 OpenAPI 3.1 附加约束保持原样；显式“展开为独立结构”即使没有继续编辑字段，也会形成可保存的独立结构，3.1 附加约束按 `allOf` 交集保留。修改引用中的嵌套字段仅展开当前拥有者，不修改被引用模型。引用型请求体/响应容器的局部 Schema 修改通过复制容器写入当前 Operation。缺失、外部、循环及条件 Schema 的原结构继续只读，但可以用本地模型整体替换。

Operation 自有参数支持展开结构设计、模型引用和字段约束。参数中的 Schema 引用不再让参数元信息全部只读；路径继承参数、共享 Parameter Object、使用 `content` 的参数及可视编辑器无法表示的直接布尔 Schema 保持只读，避免写入互斥的 `schema` 与 `content`。参数草稿延续工作区/规范/Operation 隔离，兼容早期没有完整 Schema 的设备草稿。

改名同步更新本地 Schema 引用、子字段指针和 discriminator 映射，示例、默认值、枚举、常量及扩展字段中的字面数据保持不变。模型删除前扫描整个定义，包含未被接口使用的公共组件；存在来自其他定义的引用时展示引用位置并禁止删除。仅被自身递归引用的未使用模型可删除。成功改名更新已打开模型标签身份；删除回到模型目录；其他 Operation 和独立的原文编辑草稿保持不变。

模型草稿按工作区/规范/引用隔离并保留未完成源码。其他 Operation 变更可基于最新规范保存；公共定义变化则阻止覆盖，允许下载和明确放弃草稿。Worker 校验期间若规范变化，停止保存过时正文；真实 412 触发刷新但保留草稿。保存完成后的清理不会移除新视图中更晚写入的草稿。设备存储失败会提示，不能视为跨设备共享草稿。目录刷新后重新加载来源、仓库和提供者环境元数据，加载期间继续禁用写入。

### 响应查看与示例

响应正文使用只读 CodeMirror，支持行号、JSON 高亮、折叠、换行、文本查找和复制字段的 JSONPath 或源值。视口以外的行按需渲染；查找可以展开命中的折叠范围。JSON 格式化仅调整空白，保留数字、重复键、键顺序与转义原文；无效和截断的正文按文本显示。正文、响应头、原始 HTTP 和实际请求分别查看，复制与下载遵循当前选中的视图。

有效且完整的 JSON 响应可切换到 jq 筛选视图，例如用 `.data[] | select(.id == 42)` 找到一条记录。执行时才在独立浏览器 Worker 加载 jq，原始 JSON 文本直接交给 jq；没有经过 JavaScript 对象转换。单条输出显示其值，多条输出以可下载的 JSON 数组呈现。查询可取消，3 秒超时，输出限制为 1,000 个结果和约 1 MiB；空结果、表达式错误及超时分别显示。筛选结果用于当前正文视图的复制、下载和文本查找。校验、断言、提取响应示例及原始 HTTP 继续使用实际响应。查询和输出只在当前工作台内存中保留。

在当前 Operation 的调试工作台中，可把实际响应提取到该接口的设计草稿。弹窗明确显示实际状态码和媒体类型：新增精确状态码、在已有状态码下新增媒体类型，或使用已有媒体定义。精确状态码是独立条目；已有状态范围、default 和共享引用保留原样。目标状态指向共享响应时不提供提取入口。提取限于不超过 32 KiB、未截断的 JSON 或文本正文，数据来源为完整响应而非筛选结果。

用户审核正文后可仅添加具名示例；目标媒体尚无 Schema 时，还可预览并应用从该示例推断的字段和类型。推断合并数组对象中观察到的字段，对混合类型使用组合 Schema，按 OpenAPI 3.0/3.1 表达可空值；空数组的元素类型及 3.0 中只有 null 的值保留为待定义。单一样本不推断必填、枚举或格式。超出可视编辑器可审阅范围时仍可仅保存示例。

提取只写本地设计草稿。已有 Schema、待保存的响应定义和同名示例不被覆盖；冲突时整次提取不写入。设计页可继续编辑响应描述、字段与示例，或为仅有示例的媒体类型手动定义 Schema。正式保存沿用 ETag 和修订。文档预览在示例上方展示请求和响应的字段结构，包含引用模型的字段及可空类型。新旧示例并存时，将旧的单值 `example` 迁入不重名的 `examples` 条目。规范序列化不能准确保留的 JSON（例如重复键或精度超限数字）必须修订后才能作为示例写入。

### 固定修订的文档分享

借鉴 Apifox 的版本发布和 Hoppscotch 的发布前快照预览，将“工作区内持续维护”与“对外阅读”分成两个入口。规范根节点的 owner/admin 可选择已保存的修订，预览完整目录、当前 Operation、引用字段及示例后显式发布。分享不包含浏览器草稿，不会随源规范更新，也不新增源规范修订。每个修订只保留一个有效链接；复制、打开、撤销与失败重试在同一管理弹窗完成。发布期间锁定标题与修订，迟到的预览不能覆盖当前选择。

`OpenApiPublication` 保存经过处理的正文、修订引用和随机 ID；SQLite/PostgreSQL 使用相同版本 21–23 迁移及级联删除规则。预览摘要在提交时复验，避免发布与审核不一致。匿名读者仅调用专用公开读取接口，按 Tag 和 Operation 导航，支持搜索、片段链接、返回/前进和下载；接口文档与模型详情复用独立阅读组件；仅在允许在线调试并进入调试 Tab 时加载隔离工作台，不读取工作区配置、环境或历史。

发布移除 OpenAPI 根、路径、操作和回调路径的运行服务器配置，保留模型中同名的 `servers` 字段。不会读取环境配置到文档；已知工作区 Secret 出现在标题或文档时拒绝发布。文档示例和其它说明仍需发布者审核，此检查不能替代内容审查。发布者可配置文档标题、说明、浅色/深色主题、下载按钮和在线调试开关。链接持有者可匿名阅读，在启用时下载定义或使用自填地址与凭据调试；撤销阻止后续访问，不能收回已经下载的副本。管理写入同事务审计；托管备份不保存公开链接，恢复后必须重新发布。随机子域名按 `<32位随机ID>.<应用域名>/` 生成，同时保留 `/docs/openapi/{id}` 路径入口。生产部署需 wildcard DNS、反向代理和 TLS；本地使用 `<id>.localhost:<port>`。密码、有效期、接口范围筛选和独立自定义域名配置尚未接入。

阅读层由 `OpenApiDocumentReader` 管理目录与选择，`OpenApiPublishedOperation` 管理文档/调试 Tab，`OpenApiOperationDocument` 组合契约模块，`OpenApiPublishedModel` 展示字段、示例及使用位置。鉴权、参数、响应和媒体内容分别由 `OpenApiSecurityDocument`、`OpenApiParameterDocument`、`OpenApiResponseDocument`、`OpenApiMediaDocument` 负责；`OpenApiSchemaPreview` 递归展示引用字段、约束、默认值和示例。`OpenApiRequestCode` 与纯函数 `openapiDocumentation.ts` 负责定义驱动的请求代码和包含鉴权的单页 Markdown。请求正文示例/媒体类型切换会重新生成代码，响应状态/媒体类型在结构与示例栏间同步；选择状态归文档容器管理。通用下拉沿用 `AppSelect`，不为公开页面另建控件体系。

内部操作文档与发布预览复用同一契约组件。宽屏将请求代码与响应示例排列在右侧，窄屏顺序阅读；目录按 Tag/Operation 与模型分别检索。公开调试要求绝对 HTTP(S) 地址，以 `credentials: omit` 发送浏览器请求，仍按定义处理参数、正文与鉴权；Cookie 和跨域访问遵循浏览器限制。发布开关控制界面能力，不能防止读者复制已公开的正文。操作流程和部署条件见[发布 OpenAPI 文档站](../guides/openapi-documentation-sites.md)。

### 调试契约校验

服务器按 Operation → Path Item → 文档选择，显式的环境 Base URL 和服务默认服务器优先于规范定义；服务器变量使用有效定义的默认值并支持调试时覆盖。集合运行逐个解析所保存 Operation 的有效服务器和变量默认值，不借用当前打开接口的服务器。带 `/v2` 等服务器路径前缀的参数替换和 URL 恢复以操作路径后缀匹配，保留前缀和参数编码。

调试工作台提供默认关闭的“发送前校验请求契约”，保留主动发送无效请求进行测试的能力。启用后，在环境插值、前置脚本和认证处理后检查必填 path/query/header/cookie、必填请求体与表单字段，并校验 JSON 请求体 Schema；失败时显示字段路径和规则且不向目标发请求。当前尚未校验所有非 JSON 正文约束或参数 Schema 的完整约束。

响应使用实际 HTTP status（精确、范围、default）和 Content-Type 选择 Schema，未声明的失败状态不会套用成功响应契约。JSON Schema 校验通过独立 Worker 中的 Ajv 执行，支持枚举、格式、字符串/数值/数组/对象约束、组合及有限数据中的递归引用；3.0 的 nullable/exclusive bounds 转换为等价 JSON Schema，3.1 使用 2020-12 校验器，并按请求/响应方向处理 readOnly/writeOnly 的必填要求。schema 编译和正则执行有 2 秒 Worker 超时，取消/离开时释放 Worker；外部/缺失引用、无法编译、超时和截断响应不能显示校验通过。错误只返回路径和规则，不返回响应值或编译代码。新请求或规范变化清除旧校验状态。切换 Operation、规范更新或离开组件时取消旧请求，迟到结果不会写入新 API 的工作台；显式取消和超时分别提示。

### 请求导入与代码生成

调试请求统一以 `WorkbenchRequest` 表示方法、显式 URL、启用的请求头、Cookie、正文及媒体类型。cURL 导入在纯解析模块中处理 Shell 单词与 cURL 参数，不执行 Shell，不展开变量，不读取路径指向的文件。POSIX 引号、续行、ANSI 字符串、短参数组合、重复数据、GET 查询、JSON、Basic/Bearer、Cookie、URL 编码及 multipart 均先生成预览，明确显示方法、目标、媒体类型和警告。未知选项、格式错误、多 URL、Shell 操作及浏览器无法发送的 GET/HEAD 正文会阻止应用，不改动原请求。

导入请求进入独立调试模式，方法默认遵循 cURL 的 GET/POST 规则；不借用当前 Operation 的方法、表单字段或认证。JSON 中的百分号不参与表单解码；URL 编码表单保留重复字段及加号语义。multipart 文件只保留待选择项与上传文件名/MIME 提示，二进制正文也需显式选择文件后才允许发送；源路径不会被自动读取。选择的文件与导入模式参与当前工作台撤销/重做和接口切换隔离，不写入规范正文。命令行连接/输出/超时参数会明确提示不生效；Web 请求继续使用浏览器的网络行为与平台 20 秒超时。

代码生成由独立纯模块将请求与临时文件选项归一化，再生成 cURL、Node.js Fetch/Axios、Python requests、Java HttpClient、Go net/http、PHP cURL、Ruby Net::HTTP 或 C# HttpClient。Cookie、媒体类型、超时、重复表单项、文件上传名称/MIME 和二进制文件进入生成结果；multipart 边界由目标客户端生成，空表单使用合法的空 multipart 正文。cURL 文件路径另按其表单参数规则处理，不能只做 Shell 转义。片段可复制与下载，Java 使用匹配公开类名的文件名；复制反馈与响应复制反馈独立。

代码预览不解析服务 Secret 或执行脚本；当前认证选择使用占位符，环境变量保留为模板。用户手动输入的请求头与正文按原值生成，界面提醒替换变量和本机路径。代码片段也不会绕过浏览器的 Cookie、CORS 或受限请求头规则。当前已实际执行 cURL、Node Fetch、Python、Go、Java 的 JSON、multipart、二进制与 GET 请求；Axios、PHP、Ruby、C# 尚未在对应运行环境执行，不能据此认定全部语言已验收。

## API 与存储基础调整

1. **摘要和正文分离**：为目录/树提供不含正文的规范摘要（ID、serviceId、title、kind、version、contentHash、updatedAt、来源摘要）；增加按 ID 读取正文的接口。为兼容现有 v1 客户端，可先增加显式 metadata 查询/目录接口并保留当前 `/catalog` 行为，后续再评估默认响应迁移。
2. **格式可判别**：规范创建请求显式包含 `kind`，旧请求缺省保持 Markdown；OpenAPI 记录 JSON/YAML 格式信息，更新时不允许悄悄改变 kind。DTO、ETag、错误目录、OpenAPI fixture 和双语验证错误同步更新。
3. **通用验证边界**：Core 负责不变量和事务；格式解析放在纯格式/文档解析能力中；API 在写入前调用；Controller 复用同一验证器。Core 的 `create_markdown_specification` 等专用方法演进为保持调用边界清晰的格式感知命令。
4. **仓库文件发现**：Repository Controller 仍只产出通用快照；文档发现按允许的文档类型筛选，Markdown 和 OpenAPI 分别校验路径、编码、大小和语义。新增 OpenAPI Document Controller 消费 RepositorySnapshot，记录 hash、commit、manifest 和诊断。
5. **实现导航投影与缓存边界**：规范实现返回的导航投影可按 `(specificationId, contentHash, providerVersion)` 在进程内缓存并随规范更新失效；持久索引只有在实测解析成本或搜索需求证明必要时再增加。禁止把缓存当作来源事实。缓存失效后必须能够从规范正文重新生成相同的节点身份。

现有 `specifications.kind` 已有文本列，Markdown 修订也保留原始文本；若不引入新持久关系，OpenAPI 类型本身不需要新表。摘要接口、环境资源和 Secret 关系仍需按 API/数据库变更规范评估 SQLite/PostgreSQL 迁移及 ETag 并发行为。

## 服务环境与请求执行

### 环境资源

新增服务归属的 `ServiceEnvironment`，建议字段包括稳定 ID、serviceId、名称、`baseUrl`、非敏感变量、认证模式、Secret 引用、是否生产环境、排序和更新时间。环境属于服务的共享配置，不放进 Specification，也不作为本机 UI 偏好。

密码、Bearer token、API key 等敏感值只能通过已有 Secret/Integration 机制引用；环境列表只返回 Secret 元数据/引用，不返回明文。创建或编辑环境使用 ETag/CAS；删除被正在使用的环境时要有明确行为。首版变量插值只允许显式的环境变量语法，不执行脚本、模板函数或任意表达式。

### Operation 认证

调试工作台默认使用该 Operation 的 `security`；未声明时继承文档要求，显式 `[]` 表示无要求。安全要求数组中的项是可选方案（OR），所选方案中的认证方式须同时应用（AND）；空对象可作为匿名方案。独立导入的请求默认不生成认证，也可以显式选择规范中定义的方案。请求中显式提供的认证头优先，重复的生成目标和缺失凭据会在发送前提示。

认证输入按方案保存到当前工作台内存，可使用临时值、完整的 `{{VARIABLE}}` 引用或当前环境中的同名变量。保存的请求只共享选择、方案和变量引用；API 再次脱敏明文输入，旧记录可省略认证配置。集合按每条请求保存的设置执行；切换环境重新解析变量。OAuth PKCE 令牌不持久化，切换环境或 Operation 后失效，迟到的授权结果被丢弃。代码片段使用占位符，自定义认证字段和历史标题一并脱敏。Cookie 认证仍受浏览器限制。

### 执行边界

请求执行是用户显式触发的一次性动作，不是 Core 事务，也不由 Repository/Markdown 控制器执行。首版不新增可接收任意 URL 的 SpecX 服务端 HTTP 代理，以免把环境地址变成 SSRF 入口并让 Core/Web Host 承担外部网络副作用。

推荐通过宿主提供的 `ApiRequestExecutor` 能力执行：浏览器 Host 使用受浏览器 CORS/Private Network Access 约束的 fetch；Tauri Host 可提供本地请求适配器，但要有明确的 Tauri capability、超时和响应大小限制。发送前显示环境、解析后的最终 URL、HTTP method；修改性请求必须由用户按下发送操作触发，生产环境给予显著提示。记录状态码、耗时、响应头白名单和受限大小的响应正文；授权头、Cookie、Secret、变量值和请求正文不得进入日志、错误消息或遥测。

浏览器 CORS 会限制部分用户服务，Tauri 与 Web 的网络行为也不完全相同。若要求 Web 部署也能绕过 CORS 或访问内网目标，应单独设计受管理员控制的执行代理：目标 allowlist、DNS/IP 重绑定防护、禁止云 metadata/loopback 的默认策略、出站网络隔离、Secret 最小权限和完整审计；该代理不纳入当前推荐的首版。

## 滚动条布局修正

问题定位在 `ServicePanel.vue` 与 `resources.css`：概览/规范节点的滚动元素同时设置了 `max-width: 1100px` 和水平居中，滚动条因此固定在居中内容框边缘；main pane 额外 padding 又缩小了滚动视口。

建议拆成两层：外层视口占满 main pane 可用宽度并负责纵向滚动；内层内容容器负责 `max-width`、居中和左右 padding。这样内容仍保持易读宽度，滚动条贴近应用主面板右缘。Service Overview、Markdown、OpenAPI 文档和 API 操作视图共用同一滚动/内容容器规则，避免每种面板各自修补。

## 分阶段实现与验收

### Story 0：资源视图与规范实现导航基础

- 资源树可以表达并展开 Group → Service → 规范实现返回的分类/规范/派生节点；服务概览和所有目录节点可打开自己的视图。
- 每个已出现的规范提供者都返回一个自动创建的提供者目录；Markdown 规范是目录下叶子，OpenAPI 规范是目录下的规范/Tag/操作投影；通用树只消费节点能力和图标元数据。
- 同一提供者目录下的多个规范稳定排序且互不覆盖；提供者目录没有规范时不创建。
- 规范目录只加载摘要，打开后按需加载正文；旧 API 客户端行为保持兼容。
- 工作区切换、标签页恢复、搜索、键盘导航、右键菜单、未保存保护和窄屏布局仍正确。
- 修正滚动视口，桌面/窄窗口验证概览、规范页滚动条贴近主 pane 右侧且内容最大宽度保持一致。

### Story 1：OpenAPI 文档生命周期

- 创建、导入、编辑、ETag 冲突、修订查看/恢复和仓库来源按类型工作。
- JSON/YAML 与支持版本校验准确；无效创建/编辑不改变服务端内容；错误含字段路径但不回显 Secret。
- OpenAPI 文件可从 RepositorySnapshot 发现和同步；有效变更产生单一修订，无效或未变化输入不产生错误修订。
- Markdown 的创建、编辑、来源限制、历史和现有 API 契约回归通过。

### Story 2：规范实现导航与 Tag/API 浏览

- 不同规范实现返回的节点可以共存；分类目录、规范目录和叶子节点的身份、打开行为和能力声明稳定。
- 同名 Tag 聚合为一个目录；无 Tag、多 Tag、未声明 Tag 和操作重命名/删除均映射稳定。
- 点击 API 操作显示完整文档；method/path/search/tag 状态与规范 hash 一致；旧版本操作标签不会误指向新操作。
- 列表支持大型规范虚拟滚动或分页，不因数百/数千操作阻塞主线程。

### Story 3：服务环境和 Try it

- 服务可创建、修改和删除多个环境；环境变量与 Base URL 在发送前按环境解析，支持 `{{name}}` 和 `<<name>>` 两种模板写法。环境名、标识和变量名在服务内唯一，敏感变量不回显。
- 发送前确认目标环境和 URL；参数、请求体、认证和媒体类型生成正确；响应状态、时长、取消/超时、大小上限和错误显示明确。
- Secret 只在执行授权时使用，不出现在列表、日志、历史记录或错误反馈；Web CORS/Tauri 网络差异有真实运行验收。
- 对 POST/PUT/PATCH/DELETE 不自动重试，不在打开页面时自动执行。

运行时解析由 `POST /services/{serviceId}/openapi/environments/{environmentId}/resolve` 提供，响应设置
`Cache-Control: no-store`，只在用户按下发送按钮后调用。请求可选择浏览器或受限云端 Agent；Agent 的目标策略、授权范围及遥测见 [API contract](api-contract.md)。暂存与保存为用例功能及共享工作台 API 已移除；请求历史保存在当前设备，会话编辑支持撤销/重做。

### 跨层检查

- Rust Core/API/SQLite/PostgreSQL、migration check、ETag/授权、错误契约和 OpenAPI fixture 同步。
- Controller 测试覆盖快照交接、有效/无效文件、重复事件、hash 去重和旧 generation 不覆盖。
- UI 覆盖中文/英文、亮/暗主题、键盘导航、菜单、编辑冲突、窄窗口和真实 HTTP 请求展示。
- 安全验收覆盖本地 `$ref` 循环、外部 `$ref` 拒绝、不安全 URL/跳转策略、响应超限、Secret 脱敏和恶意 OpenAPI 字符串不作为 HTML 执行。

## 首版不做

- OAS 2.0/Swagger 转换、远程 `$ref` 获取、规范合并/生成器、mock server、数据驱动集合自动化、浏览器 cookie 注入、Webhook/回调执行。
- 将每个 operation、Tag 或解析出的 schema 独立写入数据库；把 arbitrary Service children 做成可执行脚本；通过通用资源表取代现有领域表。
- 面向互联网开放的服务端请求代理和任意插件运行时。

## 需要对齐的决策

1. 是否确认服务只负责承载规范实现返回的子树，不在服务下继续创建嵌套服务？
2. 是否确认每个规范提供者都必须提供自动创建的目录、名称和图标，目录下再由实现决定规范/Tag/操作层级？
3. OpenAPI Tag 目录由规范内容自动生成是否足够，还是还需要用户手工维护的额外目录？
4. 首版是否接受 OAS 3.0/3.1、JSON/YAML、仅本地 `$ref` 的支持范围？
5. 首版 Try it 是否接受 Web 使用浏览器 CORS、Tauri 使用本地执行器，暂不做服务端代理？Secret 是否必须在首版持久绑定环境，还是可先限定为安全的执行时凭据？
